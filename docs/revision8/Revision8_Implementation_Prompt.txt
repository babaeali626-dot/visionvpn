PHASE 3 — HIDDIFY-STYLE CHAIN MODEL AND USER EXPERIENCE

Use the official Hiddify Chain documentation to implement the semantics, not merely the visual stack. The two optional roles are independent and have different meanings:

1. Proxy Unblocker / Entry Layer:
   - WARP or Psiphon is used before the user's main proxy profile to help reach a profile/server that is blocked or filtered on the user's normal network.
   - The main profile is still the endpoint provider unless an Extra Security layer is also configured.

2. Extra Security / Final Exit Layer:
   - The user's main proxy is reached first; WARP or Psiphon is then used after it as the final Internet exit.
   - This prevents the main proxy operator from seeing the user's final destination traffic in the same way as a direct exit, and websites see the actual WARP/Psiphon exit IP rather than the main proxy's IP.
   - The Public Exit card must identify this last provider and show its actual verified country/flag/IP.

3. Both layers can be enabled together only when the route graph, transports, ports, capabilities, and resource limits make the topology valid. If the same engine/provider is requested twice, either support separate engine instances with distinct config/data directories/ports and independent lifecycle ownership, or reject the topology with an actionable explanation. Never silently collapse two hops into one.

4. Make packet direction unambiguous in the UI. The underlying packet path is:
   App traffic -> Proxy Unblocker (if enabled) -> Main Profile -> Extra Security (if enabled) -> Internet.
   The on-screen layout may visually resemble Hiddify, but arrows, labels, and final-IP indicator must not imply the wrong packet order.

5. Add explicit selectors for:
   - Main profile (existing remote/built-in profile selection).
   - Extra Security: Off / Cloudflare WARP / Psiphon.
   - Proxy Unblocker: Off / Cloudflare WARP / Psiphon.
   - Region options for Psiphon where supported.
   - WARP tunnel/provider options only when genuinely implemented and tested.

6. Show a live validated chain preview with role names, actual start/end status, and final exit ownership. Clearly display which layer is the Final IP provider. Example fixture: Extra Security = Psiphon (requested US), Main Profile = a user-selected subscription, Proxy Unblocker = Off. Never hardcode the screenshot's “Ali Subscription” label.

7. Extend `ChainConfig`/`RoutingGraph` carefully. Preserve compatibility with existing `primaryExitType`, `secondaryExitTypes`, standalone Tor/Psiphon/WARP profiles, Tor-entry modes, custom exits, and stored user configurations. Use explicit versioned migration rather than deleting or reinterpreting old chain fields silently.

8. Validate protocol capabilities, TCP/UDP support, upstream SOCKS support, UDP requirements, transport compatibility, recursive/circular routes, duplicate engines, loopback port collisions, TUN DNS, and engine order before starting anything.

9. Reuse the existing `ChainManager`, `LocalEngineManager`, `RoutingGraph`, `LibboxRuntime`, and fail-closed cleanup logic. Maintain correct pre-core/post-core engine startup and reverse-order shutdown. On failure or cancellation, stop every started child engine and confirm cleanup before releasing leases or TUN ownership.

   - Main Profile only.
   - Main Profile -> Extra Security WARP.
